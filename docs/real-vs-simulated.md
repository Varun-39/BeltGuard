# What is real, what is simulated

*BeltGuard — SIH PS 26008. Last updated 2026-09-09.*

This document exists so nobody on the team ever has to guess what we can
honestly claim. **A well-built simulation is respectable. A project that lets
people assume fake data is real is not.** If a judge asks "is that a real
conveyor?", the answer below is the answer.

---

## The one-sentence version

> The AI models are real and trained on real data. The sensor readings are
> simulated, because we have no hardware — and the system says so on screen,
> on the wire, and in every alert it sends.

---

## Component by component

| Component | Status | What that means exactly |
|---|---|---|
| **Defect detection model** | 🟢 **Real** | YOLOv8n trained by us on 1,573 real photographs of damaged conveyor belts (Roboflow, CC BY 4.0). 120 epochs on an RTX 5060. Test mAP50 **0.976**. |
| **Vision inference** | 🟢 **Real** | Real ONNX inference on real images at ~62 img/s. Nothing about the detection is faked. |
| **Vibration indicators** | 🟢 **Validated on real data** | RMS / kurtosis / crest factor are validated against the **CWRU bearing dataset** — 1,537 windows from 16 real accelerometer recordings. An anomaly detector trained only on healthy data catches 100% of real bearing faults at an unseen motor load, with a 3.4% false-alarm rate. |
| **Sensor readings** (vibration, temperature, load, speed, acoustic) | 🔴 **Simulated** | Generated by `sensors_sim/`. No physical sensors exist. Every reading carries `simulated: true` from the generator through MQTT to the dashboard badge and the Modbus `DATA_SIMULATED` register. |
| **Fusion & health scoring** | 🟢 **Real logic, simulated inputs** | The rule engine, thresholds and evidence are exactly what would run on a real belt. Only its inputs are synthetic. |
| **RUL / predicted life** | 🟡 **Real method, honestly limited** | Genuine degradation-trend extrapolation with confidence bounds — **not** a learned RUL model, and labelled as such in the UI. |
| **MQTT / backend / dashboard / SCADA** | 🟢 **Real** | Real broker, real WebSocket, real Modbus/TCP verified against an independent client. These are production-shaped, not mocked. |
| **Alerting** | 🟡 **Real code, off by default** | Real SMTP escalation. With no mail server configured it logs the alert and reports `delivered: false` rather than pretending. |
| **Jetson Nano edge deployment** | 🔴 **Not done** | No hardware in hand. ONNX is exported and the swap path is documented, but nothing has run on a Nano. |
| **Thermal camera** | 🔴 **Not built** | In the PS scope; we detect overheating from a temperature sensor instead. |

## How honesty is enforced in code, not by discipline

This matters more than a promise, because it survives us forgetting:

- `Reading.simulated` is a **required** field on the dataclass, not a default.
  A new sensor cannot be written without declaring what it is.
- The flag travels the whole path: generator → MQTT payload → backend fusion →
  WebSocket frame → dashboard badge → Modbus register 9 → alert subject line.
- The dashboard shows a per-source badge (`vibration · sim`, `camera · real`)
  and a header chip reading **"simulated data"** whenever any source is synthetic.
- Alerts generated from simulated sources say `[SIMULATED DATA]` in the subject
  **and** the body.

There is no configuration that makes simulated data look real.

## Numbers we must not overstate

These are the honest caveats. Say them before a judge finds them.

**1. `belt_joint` is validated on 7 test instances.**
It scores recall 1.000 / mAP50 0.995 — but that means *"found all 7 of 7."* One
miss would read 0.857, and the Wilson 95% lower bound on 7/7 is ~0.65. The
headline class for a problem statement about belt joints is the class we can
say least about. **Never quote 0.995 without the n=7 beside it.** The class is
scarce everywhere: 60 train / 14 val / 7 test.

**2. The CWRU 100% is an easy benchmark, not a strong model.**
CWRU uses *seeded* 0.007″ defects — large and distinct, separable on kurtosis
alone (normal ~2.9 vs outer race ~7.8). We evaluated on a **held-out motor
load** rather than a random window split (the usual way CWRU results get
inflated) and it still scored 100%, so the number is honest — but real idler
wear is gradual and messier. Expect worse on a live site.

**3. The demo timeline is accelerated 672×.**
A real splice degrades over 2–4 weeks; the scenario compresses that into 45
simulated minutes. The fault *ramp* is accelerated — belt revolutions, thermal
lag and bearing defect frequencies still run at real rates. RUL reports the
field-timescale equivalent so nothing implies belts fail in an afternoon.

**4. `belt_body` reads as failed continuously in the `testset` camera demo.**
Those images are macro shots of severely damaged belts where a tear fills over
half the frame. The area thresholds assume a wide-angle camera seeing full belt
width, so they saturate — **correctly for that framing**. Mount height, lens and
belt width are commissioning parameters, documented in `backend/fusion.py`.

**5. Maintenance downtime figures are industry-typical, not NMDC-measured.**
The "45 min planned vs 8–14 h unplanned" contrast in the dashboard is an
estimate. It is labelled as such on screen.

## Questions we should expect, and the honest answer

**"Is this running on real hardware?"**
No. No sensors, no camera rig, no Jetson. Everything is built so that swapping
in hardware is a `DataSource` implementation and a config change — see
[hardware-swap.md](hardware-swap.md) — but that swap has not been done.

**"So the whole thing is fake?"**
No. The vision model is real and trained by us on real belt damage. The
vibration indicators are validated against a real bearing dataset. The broker,
backend, dashboard and Modbus bridge are real software. What is synthetic is
the *sensor signal*, because a sensor needs a belt.

**"Why should I believe the simulator is realistic?"**
Because its fault signatures come from published failure physics — bearing
defect frequencies derived from bearing geometry (BPFO/BPFI), first-order
thermal lag, 1×/2× misalignment harmonics — and because the indicators it
produces are the same ones that separate real faults in the CWRU data. That
last point is the check: if our indicators only worked on our own simulator, we
would have found out.

**"What would it take to make this real?"**
An accelerometer, a temperature probe, a load cell, a camera and a Jetson Nano.
The estimate and the wiring are in [hardware-swap.md](hardware-swap.md).
